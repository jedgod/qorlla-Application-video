# Security Shield: Main App and Qorlla Meet integration (v2.2)

**Status: wired and tested across the REAL main app (`server.js`), the REAL Qorlla Meet (`qorlla-meet-video/server/index.js`) and the REAL voice engine, on real PostgreSQL, over HTTP/WebSocket with real signed workload credentials (7 integration tests, `qorlla-voice-engine/test/shield-integration.pg.test.mjs`). Branch `integration/shield-main-app-meet`. Enforcement is OFF unless configured (`SHIELD_SYNC_URL` on the main app, `SHIELD_MEET_ENFORCE=true` on Meet, `SHIELD_ENFORCE=true` on the engine). Release remains BLOCKED.**

## Who is the authority for what
| Fact | Authority | Shield's copy |
|---|---|---|
| Account exists, email verified, suspended by an account administrator | **Main app** (`auth.js`), reported through `shield-bridge.js` | `shield_principals`, `qphone_accounts` (Numbers & Plans) |
| Organization (tenant) of an account | the authoritative backend / operator (not the main app, which has no tenants); the main app's sync **never overwrites it** | `shield_principals.org_id` |
| Meetings, passcodes, waiting room, host approval | **Qorlla Meet** | `shield_meetings` (policy facts only: host account, organization, guests allowed, end time; **never the passcode**) |
| Whether a signaling session may be opened or kept | the **Shield** | `shield_events` (append-only) |
| Phone numbers | **Numbers & Plans** (see `VOICE_NUMBER_SYNC.md`) | `voice_number_projection` |
Suspension is a set of **holds**: the main app's administrators and security operations each place their own; only the party that placed a hold can lift it, and the account stays suspended while any hold remains (the main app's periodic reconcile cannot silently undo an operator's emergency suspension; this was found by a flaky integration test and fixed).

## What is enforced where
- **Main app**: every account change (register, email verify, email change, suspend/restore) is queued to the shield and to Numbers & Plans and retried until accepted; a full reconcile runs at start and every `SHIELD_RECONCILE_SECONDS` (default 300). A suspended account has no usable session anywhere (`getUser` returns nothing), cannot sign in, and is signed out everywhere. `POST /api/admin/accounts/:id/suspend` (accounts in `PHONE_ADMIN_USERS`; not yourself). With `SHIELD_REQUIRE_VERIFIED=true` an unverified account gets no voice token (`verification_required`). The main app signs workload credentials with a key of its own, published at `/.well-known/shield-workload-jwks.json`.
- **Hand-off to Meet**: the main app tells Meet the host account of each scheduled meeting and the account behind each join, **only over the bridge secret**. A browser-supplied account id is ignored (the participant stays a guest).
- **Meet (signaling gate)**: with `SHIELD_MEET_ENFORCE=true`, a socket is accepted only if (1) Meet's own checks pass (token, meeting not ended, participant **admitted by the host / waiting room**) **and** (2) the shield authorizes it. The shield decides `kind`: *host* (only the registered host account, verified, not suspended), *member* (verified, same organization), or *guest* (no account, an unverified account, or another organization **where the meeting allows guests**). Guests/unverified get `meeting.join/media/chat` only. Anonymous meeting creation is refused. Sessions are **re-checked every `SHIELD_RECHECK_SECONDS`** (default 15): a suspended or unknown account, or an ended meeting, is disconnected (`session_revoked`) and its participant marked denied so the token cannot come back. If the shield cannot be reached for `SHIELD_RECHECK_GRACE_SECONDS` (default 120), open sessions are closed; **new** sessions are refused at once. A Meet with enforcement on but no shield configured refuses everything.
- **Engine**: with `SHIELD_ENFORCE=true` every voice API call needs a known, **verified**, unsuspended account whose token was issued after the last revocation; an unverified account can only ask where it stands (`/v1/voice/me`, `/v1/voice/numbers/me`, `/v1/shield/authorize`). Guests have no voice identity, extension, number or PSTN path (their credentials are not voice credentials). Suspension closes voice sockets (4003), kills outstanding PSTN authorizations and lists live PSTN calls for the gateway to hang up.

## Verified against the running services (7 tests, 3 consecutive passes)
Registration/verification sync to both the shield and Numbers & Plans; no voice token until verified; engine refusal of an unverified principal independent of the main app; suspension from the main app admin API through to the main-app session, sign-in, engine token refusal and **voice WebSocket termination (4003)**, then restore; guests cannot create meetings, wrong passcode refused, waiting-room guest gets no session until the host admits, host credential used by another/no account refused, browser-claimed account ignored, approved guest has guest rights only and cannot end/admit/read the waiting list or reach another meeting, guest credentials are not voice credentials, no guest extension; unverified account admitted as a guest only (refused in members-only meetings); member suspended mid-meeting is disconnected and cannot reconnect; cross-organization refusal and guest-only outsiders; workload credential replay, wrong scope, unlisted subject, anonymous and shared-secret use refused; international / premium / unowned-caller-ID PSTN denied, emergency suspension of an account with a live PSTN call lists it for termination and records the outcome; shield unreachable or unconfigured: no host, member or guest session.

## NOT done (release stays BLOCKED)
- **There is no media server in this repository** (Meet is peer-to-peer WebRTC with socket.io signaling). The shield gates the signaling session, the only gate that exists; a participant already holding another peer's connection details is not stopped at media level. Real media-gateway enforcement needs an SFU/TURN admission path, which is a separate infrastructure decision.
- **Workload identity is application-layer JWT** from a key each service holds; the test issuer is a stand-in. Production needs mTLS or SPIFFE/SPIRE with rotation and revocation. No key rotation procedure exists.
- **MFA, device trust, suspicious-session detection, alerting/SIEM, incident playbooks** are not built. Account takeover defense today = suspension + token revocation + verification.
- The main app has **no organizations**; tenancy comes from whoever assigns `shield_principals.org_id` (no admin UI/API in the main app for it). Meetings registered with Meet **before** this change have no host account recorded, so under enforcement their host is refused until re-registered (backfill not written).
- Only **voice** and **Meet signaling** are gated for unverified accounts. Chat/messaging, workplace and other main-app features are not yet restricted until verification.
- HTTP routes in Meet (chat export, etc.) rely on the participant's admitted state; a suspended member loses them at the next re-check (<= `SHIELD_RECHECK_SECONDS`), not instantly.
- The Meet re-check adds one shield call per interval per Meet process; not load-tested. The Twilio adapter, carrier, TURN, multi-host, PostgreSQL failover and physical-device gates are unchanged and open.
- Regression: engine suite 136/136; main-app Playwright (chromium, 1 worker) login-hardening, lockout, guest, guest-security, guest-welcome, meet-handoff, passcode-server, voice-engine: 75/75 (they ran against the test Meet on :3310, which is the OLD Meet without the shield changes; the new Meet code is exercised only by the integration test). The full Playwright suite was not run.
