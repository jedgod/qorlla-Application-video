# Windows and Android meeting participation: certification report

**Status: engineering-verified on this machine, NOT production certified. No signed installer, no store build, no cross-network or TURN evidence; physical-device evidence is one Android phone (Galaxy A03s) on the same Wi-Fi as the PC. Every release gate in `RELEASE_GATES.md` that was BLOCKED stays BLOCKED.**
**Code under test: `c35afc32ce7bbd8f8f9e5ec84c495583eba395d8`** (branch `integration/installable-clients`, from the A3.7.1 head `2ce2894`; not pushed). Raw outputs: `docs/evidence/clients/` (with `ENVIRONMENT.txt`: versions and the SHA-256 of the test APK).
**Physical-phone results** used the same app code with an arm64 build (APK SHA-256 in `docs/evidence/clients/ENVIRONMENT.txt`) and the test harness at `9400295` (adds phone safety and diagnostics).

## What "participation" was proven to mean here
A real client application joins a real Qorlla Meet meeting (the existing web client and media path, served from the dev stack on :3310, signaling over PostgreSQL-backed Meet) that a separate Chromium participant is hosting, and **real RTP bytes flow in both directions** between them. Evidence is the participants' own `RTCPeerConnection` statistics sampled 3-4 seconds apart (audio and video bytes in and out, frames encoded and decoded, selected candidate pairs). Nothing is stubbed: the main server, Meet, the database, the host browser and the clients under test are all real.

## Defects found by running the real clients, and fixed
1. **The starter's Android app only opened the system browser** (`Linking.openURL`); a meeting could not run inside the app. Replaced by an in-app locked-down WebView.
2. **The starter's desktop shell allowed one origin only.** Meet runs on its own origin (a separate port in the nginx config, `localhost:3310` in the dev stack), so the hand-off from the pre-join page to the meeting would have been blocked. Added an explicit trusted-origin list (app + Meet, https only).
3. **Deep links accepted extra path segments and parameters** (`qorlla://join/../x?meeting=...&next=https://...`) in both clients. Now only `qorlla://join?meeting=<11 digits>` is accepted (tests for the smuggling cases).
4. **react-native-webview opened the system browser for the Meet URL**: it tests `originWhitelist` against the bare origin, so patterns ending in `/*` never match, and it hands any miss to the browser *before* our handler runs. The WebView now uses one exact-origin handler as the single decision point.
5. **Android layout:** my first version drew a native "Leave" button over Meet's own header and let the status bar overlap the app. Removed the overlay (Meet has its own end-call button; Back leaves the room) and added the status-bar inset.
6. **Test harness traps that were real findings:** `ELECTRON_RUN_AS_NODE` set by some terminals makes Electron start as plain Node; Android stops prompting after two denials, so each scenario needs a clean install; a loosely matched "Allow" button could have tapped another app's dialog, so the automation now taps only the app, the system permission dialog and the system "not responding" dialog.

## Findings NOT fixed (read these)
- **Windows: intermittent loss of the local camera track in the Electron 33 client.** In 3 of 7 default-setting runs of the join test (and in one diagnostic run) the client's video track ended by itself about 2 s after joining (no `stop()` call from page code, followed by a `devicechange`), so it sent no video (`videoOut: 0`). Some of those runs had a Gradle build or an emulator running; some were after those were stopped (idle Gradle daemons were still resident), so I cannot attribute it to load. The same join with a plain Chromium guest sent video (checked once). The same loss reproduced in a bare Electron window with a fake camera and a loopback WebRTC connection (2 of 8 runs). It did not occur in the last 6 runs (3 default, 3 with GPU acceleration off). I did not isolate the cause (Electron 33 / GPU capture path / load). `QORLLA_TEST_DISABLE_GPU=1` is provided as a diagnostic and was not shown to be a fix: 6 of 6 recent runs passed either way, so the evidence does not separate it from chance. **Real cameras were not tested; a physical-camera run and a newer Electron are needed before this can be called safe.**
- **The Meet web client does not recover when its camera track ends.** The person would stay in the room sending no video. That is a Meet client issue, outside these clients.
- **Android emulator was run once with the final APK** (and once on the build before the layout change); the physical phone has 2 full runs. Still thin.
- **An emulator, a synthetic camera and a synthetic microphone** were used. The camera showed the emulator's virtual scene.

## Not done / BLOCKED (unchanged gates)
Cross-network TURN: the phone and the PC were on the same Wi-Fi, so media took a direct local path and no TURN relay was exercised; only one phone model was tested; Windows code signing, installer, SmartScreen, auto-update, signed manifest in a real update flow; macOS, Linux, iOS; Play/App Store builds (the Android artifact is a **debug-signed x86_64 test APK**, not an AAB); native push, CallKit/ConnectionService, calling to phone numbers; screen sharing end to end (the consent prompt exists but was not exercised); accessibility and localisation review; sessions longer than about 30 seconds; more than two participants; ICE restart and network switching; battery, thermal and memory behaviour; device registry and live-session revocation integration; the MFA/identity chain (guests only were tested).

**The physical-phone runs were done with the phone owner's go-ahead (they connected the phone after being asked).** A debuggable test build was installed, only that app's permission dialogs were tapped (the automation refuses to tap any other app), the phone was never unlocked by the automation, and afterwards the test app was uninstalled and its two port mappings removed. **The real camera showed a person**, so no phone screenshots are committed. The first emulator image I tried had a Google account signed in and Google showed a security prompt on it; I did not interact with it and switched to a clean, account-free emulator (`qorlla-cert`).

## How to reproduce
Prerequisites: the dev stack (PostgreSQL on 35432, Meet on :3310), `npm install` in `apps/desktop` and `apps/mobile`, Playwright at the repository root.
- Windows: `cd qorlla-clients && node --test e2e/windows-meeting.test.cjs` (needs `ELECTRON_RUN_AS_NODE` unset; the test unsets it).
- Android test APK: in `apps/mobile`, `set QORLLA_TEST_BUILD=1 EXPO_PUBLIC_QORLLA_TEST_BUILD=1 EXPO_PUBLIC_QORLLA_URL=http://localhost:5293/ EXPO_PUBLIC_QORLLA_MEET_URLS=http://localhost:3310/`, `npx expo prebuild --platform android --no-install --clean`, then in `android/` `gradlew assembleRelease -PreactNativeArchitectures=x86_64` with JDK 17-21 and the Android SDK. The first build took about 70 minutes on this slow link (downloads, then about 25 minutes of compilation); incremental rebuilds took 1-3 minutes. Start an emulator (`qorlla-cert`: Android 15 `google_apis` x86_64, 4 GB, host GPU) and run `node --test e2e/android-meeting.test.cjs`.
- Physical phone: build with `-PreactNativeArchitectures=arm64-v8a`, unlock the phone, keep it on the same Wi-Fi as the PC, then `set QORLLA_ANDROID_SERIAL=<its serial>` and run the same command (the test uninstalls the app when it finishes). An emulator is used unless a serial is named.
- The Android build flag is a build-time switch: a store build made without it keeps cleartext traffic off and the WebView non-debuggable (a unit test checks `eas.json`'s production profile cannot carry the flag).
